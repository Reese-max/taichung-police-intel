# Issue #62 — Production closure evidence contract

Issue #62 is a closure track, not a substitute for the individual feature
issues. This document records the code-backed part of the closure work and
keeps operational evidence separate from local or CI evidence.

## Release manifest

`apps/web/public/data/release.json` is the machine-readable binding for one
Pages publication and its Worker query projection. It records:

- `release_id` and the reviewed `code_sha`;
- raw-byte hashes for feed, source status, brief, and source policy;
- `publication_generation`, `publication_hash`, and `source_policy_hash`;
- the Worker `query_generation`, `worker_version`, and stable
  `evidence_catalog_hash`;
- Pages deployment metadata plus `built_at`, `deployed_at`, and
  `anonymous_http_verified_at`.

The checked-in manifest is a deterministic fixture with deployment status
`PENDING`; it is not a production deployment receipt. The Pages workflow
rebuilds it from the exact generated bytes using:

```bash
node apps/web/scripts/sync-source-policy.mjs
python -X utf8 scripts/release-manifest.py build \
  --code-sha "$GITHUB_SHA" \
  --pages-url "https://reese-max.github.io/taichung-police-intel" \
  --deployment-id "$GITHUB_RUN_ID"
```

The Worker fetches `release.json` before serving `/health`, `/capabilities`,
`/query`, or `/mcp`. It fails closed when the manifest does not match the
served artifact hashes, publication generation, source policy, query
generation, evidence catalog, or Worker version. The production verifier also
checks the same release ID over anonymous Pages and Worker HTTP.

Generate the manifest after all publication and source-policy writes. The
`verify` command checks the sibling publication files byte for byte; Git pins
the four bound fixtures to LF so their hashes survive Windows checkouts.
Stable evidence uses source freshness when item freshness is absent and
UTF-16 ordering for IDs in both Python and JavaScript.

The production verifier validates the manifest identity and binds health,
capabilities, publication receipts, and search results to the same release.
`code_sha` identifies the Pages build; the Worker echoes that publication
identity. It is not an attestation of the deployed Worker binary: deployment
provenance still requires a separate Cloudflare deployment receipt.

## Evidence boundary

The following remain operational acceptance items and must be backed by fresh
receipts before calling the roadmap complete:

- an executed Worker deployment and anonymous smoke for `/health`,
  `/capabilities`, `/query`, and `/mcp`;
- a seven-day per-source canary with source-specific freshness policy;
- human-labelled holdout and the first fixed-user task evaluation;
- a current PR/Issue supersession inventory and the remaining UI/operator
  workflow evidence.

CI, checked-in fixtures, and local tests prove the contracts but do not stand
in for those live or human receipts.
