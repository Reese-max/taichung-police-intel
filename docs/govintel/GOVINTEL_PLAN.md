README 已記載五個定期官方來源介接及既有證據導覽；「市議會、市政會議、警察局、消防局、交通局、新聞局」則是使用者規劃的六類監測範圍，不能混稱為六個已完整串接的機關。[R7]

### 1.1 必須保留的既有基礎

- 保留來源健康、日期區間完整性、資訊缺口與最後有效資料的區別。
- 保留公告／影片的正式來源入口；轉錄文字只作導航，不當成已人工驗證的逐字真相。
- 沿用版本資料、內容雜湊、首次建立基線不產生 `NEW` 的規則，以及不完整快照不得推論移除的保護。
- 現有 `ChangeEvent.event_id` 是「文件異動紀錄」識別碼；新增跨來源公共事件必須使用另外的 `public_event_id`，不得混用或直接改寫語意。
- 既有 `feed_item_to_version` 已見欄位以標題、網址、委員會、日期與里程碑為主。全文段落及精細管制欄位是否另有實作，必須先搜尋儲存庫，不能直接假設全部缺失。[R7]

## 2. 產品目標與首期邊界

主要使用者是警政幕僚、議會聯絡、公開資訊交班承辦人及審閱主管。原本議會備詢的查證流程繼續保留，不改成即時勤務指揮平台。

首期任務：承辦人準備交班時，核對大型活動及交通管制公告，找出時間、地點、範圍或狀態的實質變更，回查原文，再產生可核對的交班草稿。

核心流程：

```text
既有官方來源／核准新增來源
→ 保存文件版本與資料時間
→ 抽取欄位及原文證據
→ 關聯同一公共事件
→ 區分重要變更、排版變更與來源失效
→ 補充有年份的 SEGIS 背景及警察機關資訊
→ 標記受影響的舊摘要
→ 人工核對／修正
→ 匯出交班草稿與引用清單
```

9 月版本必備：一個跨來源案例、兩類內政資料、可點擊文字證據、重要異動及摘要待更新提示、單人核對匯出、初步測試結果。

首期不做：全臺全面覆蓋、所有直播即時轉錄、多層知識圖譜、完整多人審批、自動對外寄送、內部勤務串接、犯罪個人風險評分或自動派遣。公開資料中的個人或敏感內容仍須排除或遮蔽，不能因網頁可讀就全面蒐集。

D1、D2 的「入口已查核」不等於「資料已下載且完成驗證」。目前主計畫採兩類資料共同使用的保守準備方式，送件時仍應向主辦確認公告與辦理計畫的用語差異。[R1、R3–R6]

### 3.1 最小來源清冊欄位

`source_id`、資料提供者、正式網址、資料集名稱、使用條件連結、允許保存／公開範圍、資料統計期、更新規律、擷取方式、負責人、逾期門檻、最近成功時間、內容雜湊與異常紀錄。

資料處理優先採官方 API／RSS／下載檔，無接口才使用經確認可用的公開頁面解析。新來源先小樣本驗證，再納入排程；不得繞過登入、存取控制或來源限制。

### 3.2 內政資料不是裝飾功能

交班卡中的「地區背景」必須顯示行政區、統計期、人口／戶數及來源；「機關資訊」顯示經確認的機關名稱、地址、電話及資料期別。兩項都必須能在任務中被核對，並納入有／無該資料的比較。

地區人口不代表活動參加人數或受影響人口。位置鄰近不代表管轄，也不代表可用警力。地名無法確定時不落精確點位；資料無值顯示未知，不補零。不以 SEGIS 歷史或模擬資料生成當日人流警報。[R3–R6]

## 4. 架構與開發方式

先沿用 Python 蒐集、V2 版本比對、Next.js 靜態展示與現有發布流程。AI 在建置端或受控後端執行，產生經結構驗證的發布資料；不把憑證或供應商金鑰放進瀏覽器。公開 Demo 可使用清楚標記時間的預先處理結果，不宣稱每次點擊都是即時推論。

RAGFlow 僅列選配的文件檢索服務；未確認既有整合，不把向量庫當作唯一版本與證據來源。不為競賽先重寫前端、強制加入新資料庫，或移除已存在的安全保護。

以下是設計契約，不表示相關檔案已經存在：

| 邊界 | 建議職責 | 驗收要求 |
|---|---|---|
| 來源介接 | 正式來源與版本擷取 | 失敗隔離、有限重試、來源頻率及授權可查 |
| 欄位抽取 | 活動、日期、狀態、機關及範圍 | 每個重要欄位有原文位置；缺值不補造 |
| 事件融合 | 同一活動的跨機關公告連結 | 不抹去各公告身份；可拆分、修正及回查 |
| 重要異動 | 在既有差異之上辨識工作影響 | 有版本前後、變更理由與下游依賴 |
| 資料補充 | 行政區人口與機關資料 | 期別、連結依據及限制明確 |
| 發布閘門 | 結構、證據、時間及敏感資訊檢查 | 未通過不得成為已確認交班內容 |
| 前端核對 | 原文、差異、衝突與交班匯出 | 來源錯誤可見；不靜默覆寫人工確認版本 |

### 4.1 資料模型：延伸而非重建

正式實作前先盤點現有 schema 與 migration，下表只規範需求。

| 實體 | 關鍵欄位／關係 |
|---|---|
| 文件版本 | 沿用 `ItemVersion`；保留 `source_id`、`stable_key`、`version_no`、原始及正規化雜湊、公告／生效／觀測時間；補充全文快照定位 |
| 文件異動 | 沿用 `ChangeEvent`；其 `event_id` 繼續指文件異動，不改指跨來源事件 |
| 公共事件 | 新增獨立 `public_event_id`、名稱、時間範圍、地點候選、關聯文件版本、合併理由及人工修正紀錄 |
| 主張／欄位 | `claim_id`、內容、事實／矛盾／待查／建議類型、來源版本、證據範圍、驗證與覆核狀態 |
| 證據定位 | 正式網址、文件版本、段落識別／頁碼／影片時間戳、必要短摘錄、擷取時間；原始快照只在授權容許範圍保存 |
| 摘要版本 | 摘要識別、輸入文件版本、主張清單、生成時間、模型／提示版本、確認狀態、需更新原因 |
| 地區背景 | 行政區代碼、資料集及統計期、人口／戶數、來源；另保存機關位置及座標系統 |
| 覆核紀錄 | 修改前後、核對時間及角色；單機版本不得假冒經身分驗證的多人審批 |

事件合併或拆分不得刪除原始文件、舊識別碼及引用關係。摘要使用版本 A，文件後來改成 B 時，將摘要標成待更新，而非直接改寫原摘要。

### 4.2 AI 與規則分工

規則掌管網址白名單、資料時間、雜湊差異、結構驗證、版本依賴、發布資格及來源故障。AI 處理非結構化欄位、跨公告語意關聯與變更理由的候選輸出；候選內容必須經規則和證據檢查。

先以日期、行政區、地點、主辦機關縮小候選，再比較文字語意。大模型相似度不是事件真相，不預先指定任意門檻為可信機率。調整只使用開發集；低把握、矛盾或關鍵時間缺失送人工處理。

重要度是「核對優先序」，不是犯罪風險或事件發生機率。優先考慮已確認的管制時間變更、影響既有摘要、期限接近與資訊衝突；來源被轉載次數不得當多個獨立佐證。

## 5. 必須守住的時間、資料與安全規則

**首次看到不等於剛發生。** 公告發布／修訂、事件生效、本系統擷取／偵測時間分開保存，缺失日期不推算成今天。

**頁面消失不等於活動取消。** 沿用完整快照及多次確認的移除保護；完整性應針對該來源與相同查詢範圍判斷，不能把分頁不全、查詢範圍縮小或其他來源成功當作本來源完整。取消必須有明確內容支持。

**健康不等於新鮮，也不等於完整。** 成功連線但資料過期仍須警示；故障保留最後有效資料及其日期。無新異動、未執行、抓取失敗、內容不完整是不同狀態。

**證據連結存在不等於支持結論。** 每個重要主張需驗證引用內容及版本是否支持；無法支持時阻擋、留白或標待查，不把拒答藏起來。

**外部內容不是操作指令。** 網頁、PDF 與字幕一律為不可信輸入。來源文字不得要求模型修改程式、讀取秘密、外傳內容、寄信或發布；隔離解析環境、限制工具權限與對外連線。

**網頁輸出與擷取安全。** 清理可執行 HTML，限制連結協定；對 URL、重新導向與下載量設限，防止任意內網擷取。來源新增需人工核准，不由文件中的連結自行擴大蒐集。

**公開與內部資料分離。** 團隊聯絡資訊、試用者資料、回饋、個別筆記及核對紀錄不提交公開儲存庫。測試前確認必要保存項目、使用同意、存放位置及刪除方式；不自行擴大為長期保存。

**降級可用。** 模型失效時仍可看來源狀態、規則差異與原文。影片失效保留正式來源入口，不拿別支示範影片冒充同一證據。公開 Demo 的合成資料、歷史重播與預先生成結果均要明示。

## 7. 測試案例最低清單

每個案例至少包含輸入版本、正確預期、產出、是否通過、測試日期及程式版本。合成案例須標示合成，不當成正式機關實際事故或活動。

| 編號 | 案例 | 正確行為 |
|---|---|---|
| T01 | 同一活動由市府、警察及交通單位各發公告 | 關聯同一公共事件，保留三份來源及內容差異 |
| T02 | 同名活動不同日期或不同地點 | 不直接合併；資訊不足時顯示候選並待確認 |
| T03 | 新聞稿被轉載多次 | 記錄衍生關係，不當多份獨立證實 |
| T04 | 只改標點、頁尾或抓取時間 | 不產生重要工作異動 |
| T05 | 管制從 17:00 改成 16:00 | 顯示新舊段落，定位受影響摘要並要求重核 |
| T06 | 正式公告取消、另一來源尚未修正 | 顯示取消依據及來源衝突，不靜默抹除差異 |
| T07 | 網站 404、分頁不完整或暫時未列項目 | 顯示來源／完整性問題，不直接判活動取消 |
| T08 | 首次匯入多年歷史清單 | 建立基線，不把所有歷史項目當今日新增 |
| T09 | 無發布日期、只有本系統偵測時間 | 明示首次偵測，不能說今日發布 |

## 8. 評測設計與成果填寫

### 8.1 資料集

目標約 300 份公開文件、60 個事件：30 個開發事件、30 個保留事件。按事件群及時間劃分；同事件的轉載、不同版本及相近案例不能跨集。保留集需包含重要修訂、無實質變更、同名異地、取消及衝突。

由兩位標註者各自判定事件歸屬、重要異動與引用支持，再裁決分歧。保留原始標註與裁決原因。模型自評只輔助檢查，不能代替人工標準答案。來源保存權利不允許全文再發布時，公開最小必要的索引、版本雜湊與評測統計。

調參只使用開發集；保留集在版本凍結後執行。若看過保留集錯誤後再調整，就須註記其已被使用，另外建立新保留案例或坦白縮小驗證強度。

### 8.2 比較方法

A：人工使用相同官方資料完成任務。  
B：既有專案 V2 規則及原有介面。  
C：本次新增融合、異動、證據及資料補充版本。

另在 C 中分別移除語意模型及 D1／D2 補充，檢查真正增益。所有方法使用相同資訊截止時間、同樣可取得的來源，不讓新系統多看未來文件。

### 8.3 目標與結果分開

| 指標 | 定義／揭露方式 | 暫定目標 | 實測欄 |
|---|---|---|---|
| 事件融合 | 同事件配對精確率、召回率及 F1；另列錯合併、漏合併和樣本數 | F1 ≥ 0.90 | 待測 |
| 重要異動 | 精確率 TP/(TP+FP)；召回率 TP/(TP+FN)，分時間／範圍／狀態 | 召回 ≥ 0.90、精確 ≥ 0.85 | 待測 |
| 引用支持 | 人工核查關鍵主張是否有正確版本與支持段落；另列無據輸出及拒答 | 關鍵主張可查，錯誤支持／無據主張以 0 件為目標 | 待測 |
| 任務效率 | 從開始閱讀至完成可交付摘要，包括核對與修改 | C 相對人工基線中位耗時下降 ≥ 30%，重要漏件不高於基線 | 待測 |
| 內政資料增益 | 背景及機關資訊正確填列率，有／無資料的任務比較 | 先實測、不預設效益；期別與來源顯示 100% | 待測 |
| 處理延遲 | 成功擷取到經驗證發布的 P95；不含等候輪詢 | ≤ 15 分鐘 | 待測 |
| 故障處理 | 故障、過期、模型失效及矛盾案例分別記錄 | 不把失敗當無事件，不錯誤覆蓋最後有效資料 | 待測 |

零分母不填 100%；應填無可評估案例並說明。不能用「全部拒答」取得零錯誤的漂亮數字，必須同時報告抽取覆蓋率、拒答率、待查數及任務完成率。小規模樣本不等於全臺泛化或正式部署成效。

### 8.4 真人試用

邀請 3–5 位相關業務使用者，每人完成 6 個任務，為三種方法各安排 2 個難度相近且不重複的案例，輪替方法順序。先訂任務清單與正確資訊，再開始計時。不要讓同一人先看過案例答案，再宣稱新工具更快。

報告人數、任務數、方法順序、案例難度、每次耗時、修正與漏件。不同使用者及案例的差異要揭露；樣本不足時只報初步描述結果，不做未支持的統計結論。

## 9. 測試執行與發布閘門

README 記載下列既有驗證指令；本次撰寫文件未執行。開發者先確認當前版本腳本仍存在，使用專案既有安裝方式與隔離測試環境，再執行。[R7]

```bash
# 在既有專案根目錄；先確認依賴與腳本內容
npm run check:gate0
npm run check:specs
npm test
npm run check
```

新增測試接入現有測試架構，而非只加一份人工勾選清單。先查看既有 publication verifier 契約，再新增事件、引用、時間及公開欄位驗證；不得用新腳本繞過原有檢查。

建議每次成果包記錄：`commit_sha`、資料清冊版本、資料截止時間、輸入雜湊、模型及提示版本、設定、測試命令、退出碼、指標分母、失敗案例與執行時間。沒有真實測試輸出就不填「通過」。

發布順序：離線規則與單元測試 → 公開來源小樣本 → 建置／瀏覽器回歸 → 保留集與真人驗證 → 核對公開內容 → 人工確認展示版本。部署及外部寫入仍按專案原有授權流程辦理。

單機匯出只表示使用者自行核對草稿，不代表具有真實身分的正式審批。正式多人版本必須另建權限、驗證與受控紀錄後才能宣稱提供審批功能。
